# Sécurité — modèle de menaces Raijin

## Actifs à protéger
1. **Le capital de l'utilisateur** : l'adresse copiée doit être exactement celle du token affiché.
2. **Le compte et les données** (réglages d'alerte, historique des signaux, paper trading ; la watchlist est archivée depuis chore/slim-down).
3. **Le projet Supabase** (service_role, quota, base).

## Menaces et parades

| Menace | Scénario | Parade |
|---|---|---|
| XSS via métadonnées de token | Un créateur nomme son token `<img src=x onerror=…>` | Interpolation Angular uniquement, jamais `innerHTML` ; sanitisation serveur ; CSP sans `unsafe-inline` pour les scripts |
| Lien piégé | `socials[].url = "javascript:…"` ou faux site de phishing | `safeExternalUrl()` serveur **et** front : https seulement, liste blanche d'hôtes pour X/Telegram |
| Spoofing visuel | Nom avec override bidi (`U+202E`) qui inverse l'affichage, ou symbole copiant un token connu | Suppression des caractères de contrôle/bidi, longueur max, affichage du mint |
| Address poisoning | L'utilisateur colle une adresse proche mais différente | Copie validée (base58 → 32 octets), confirmation visuelle des 4 premiers et 4 derniers caractères, jamais d'adresse saisie à la main |
| Données externes corrompues | API qui renvoie des types inattendus, NaN, chaînes géantes | Validation zod, `check` constraints Postgres, rejet ligne par ligne |
| Abus de l'Edge Function | Quelqu'un appelle `scan-tokens`, `enrich-tokens`, `label-outcomes`, `paper-engine` ou `backtest-run` en boucle (`scan-early` et `track-fast` ont été supprimés le 21/11/2026 : à effacer du projet distant) pour épuiser les quotas (DexScreener, GeckoTerminal, RugCheck, Jupiter) | `x-cron-secret` (même `CRON_SECRET` pour les cinq) comparé en temps constant avant tout travail, `verify_jwt=false` assumé, réponse 401 sans détail, POST uniquement (405 sinon) ; `label-outcomes` est en plus borné par appel (lab-v2 : ≤ 5 requêtes GeckoTerminal espacées de 8 s, une seule par ligne ou par fenêtre de bougies, ≤ 8 éléments étiquettes + bougies, aucune nouvelle requête après 40 s, annulation à 50 s ; **le premier 429 arrête l'appel**, sans nouvel essai ; ≤ 200 rattrapages toutes les 10 min ; seules les lignes dont le point de contrôle `next_label_at` est atteint sont relues ; cron toutes les 2 min aux minutes impaires, une ligne de comptes `label_runs` par appel) ; `scan-tokens` : budget de temps par scan (annulation de toutes les requêtes externes à 38 s, pire cas ≈ 45 s), garde anti-chevauchement (un scan plus ancien non terminé depuis < 90 s → `200 { skipped: 'overlap' }`, donc jamais deux scans en même temps ni d'alertes en double), arrêt d'un groupe de sources au premier 429 |
| Données d'enrichissement hostiles | RugCheck renvoie un nom de risque `<script>` ou avec override bidi, ou un `graphInsidersDetected` négatif/texte (→ inconnu) ; Jupiter/GeckoTerminal renvoient des montants absurdes, `NaN`, des chaînes géantes, des bougies invalides (ligne ignorée une à une) | zod sur chaque réponse (`_shared/enrich-schemas.ts`), validation élément par élément (un risque ou un pool invalide est ignoré, pas toute la réponse) ; noms de risques passés dans `sanitizeText` (≤ 40 caractères, ≤ 5) ; montants en chaînes d'entiers (`^\d{1,30}$`) calculés en BigInt ; valeurs bornées aux `check` Postgres avant écriture (sinon `null`) |
| SSRF / injection d'URL via un mint | Un mint piégé (`../`, `&amount=…`) modifie l'URL appelée | Mint (et pool) validés par `isSolanaAddress()` avant toute construction d'URL **et** `encodeURIComponent` / `URLSearchParams` ; hôtes fixes en https (`lite-api.jup.ag`, `api.jup.ag`, `api.rugcheck.xyz`, `api.geckoterminal.com`) revérifiés par `getJson()` (URL parsée, pas d'identifiants ni de port) ; `label-outcomes` n'appelle que `api.geckoterminal.com` (`_shared/gecko-history.ts`, même contrôle d'hôte) ; la variation de SOL du scan (et les prix SOL / EURC, même requête) passe par `getJson()` sur un hôte Jupiter ; les sources de candidats du scan (`_shared/source-clients.ts`) **et toutes les autres requêtes de `scan-tokens`** (paires DexScreener, audits Jupiter : plus aucun `fetch` direct ; une redirection Jupiter ne peut donc plus transmettre `x-api-key`) passent par `getJson()` avec la liste `SOURCE_HOSTS` = `api.dexscreener.com`, `api.geckoterminal.com`, `lite-api.jup.ag`, `api.jup.ag` et des chemins fixes (`/token-profiles/latest/v1`, `/token-boosts/{latest,top}/v1`, `/community-takeovers/latest/v1`, `/latest/dex/search?q=<mot-clé encodé>`, `/api/v2/networks/solana/trending_pools?duration=1h&page=1..2`, `/api/v2/networks/solana/dexes/pumpswap/pools?sort=h24_tx_count_desc&page=1`, `/api/v2/networks/solana/new_pools?page=1`, `/tokens/v2/recent`, `/tokens/v2/search?query=<≤ 20 mints validés>`, `/tokens/v1/solana/<≤ 30 mints validés>`) ; la **sonde de détection** du scan (feat/calm-sl-test, `_shared/detection-probe.ts`) n'appelle que les clients d'`enrich-tokens` sur `ENRICH_HOSTS` : `api.rugcheck.xyz/v1/tokens/<mint validé, encodé>/report/summary` (≤ 4 par scan) et `/swap/v1/quote` Jupiter (≤ 2 allers-retours, montants en BigInt, derrière le rythmeur Jupiter du scan, `x-api-key` jamais hors d'un hôte Jupiter), réponses validées par zod (`RugSummarySchema`, `JupQuoteSchema`), annulées par le budget du scan (aucun achat après 30 s, aucune revente après 34 s, tout annulé à 38 s) ; les éléments de `recent` et des listes de pools sont validés par zod un par un (≤ 200 / ≤ 100 lus) ; aucun mint venant de ces listes n'entre dans une URL sans `isSolanaAddress()` ; `JUP_API_BASE` n'est accepté que sur un hôte Jupiter ; `redirect: 'error'` ; timeout 8 s (5 s pour SOL) ; corps ≤ 2 Mo |
| Sources de candidats hostiles | Une liste (GeckoTerminal, Jupiter, DexScreener) renvoie des identifiants piégés, des milliers d'entrées, des étiquettes géantes, ou tombe en panne | zod élément par élément (`_shared/source-clients.ts`), mints validés (`isSolanaAddress`, préfixe `solana_` vérifié pour GeckoTerminal), ≤ 100 mints par source, ≤ 450 mints chargés, une source en échec n'arrête pas les autres ; `tokens.sources` borné par `check` (liste blanche de 19 noms (anciens noms conservés pour l’historique), ≤ 10 éléments, pas de `null`) et `scan_runs.source_counts` (objet `jsonb` ≤ 8 Ko) ; `sol_usd` / `eur_usd` bornés (0–100 000, 0,5–2, `NaN`/`Infinity` refusés) ; mêmes filtres de capitalisation/liquidité qu'avant |
| Lecture non autorisée | Requête avec la clé anon (publique) | RLS : `anon` n'a aucun droit ; lecture réservée à `authenticated` |
| Falsification des détections / de l'historique archivé | Un utilisateur écrit de faux résultats dans `signal_outcomes`, `preset_signals` ou dans une table archivée (`model_weights`, `early_*`, `fast_*`, `watchlist`) | RLS activée partout (rien n'est supprimé), politique **SELECT seule** pour `authenticated` sur les tables de mesure, `anon` rien ; écritures service_role uniquement ; les tables archivées ne sont plus écrites ni lues par aucune fonction (`docs/ARCHIVE.md`) ; le modèle ×3 n'existe plus (aucune probabilité calculée ni affichée) |
| Falsification des mesures de presets | Un utilisateur écrit de faux résultats dans `preset_signals` pour embellir un preset, ou lit des données d'un autre via `performance_breakdown` | `preset_signals` : RLS activée, politique **SELECT seule** pour `authenticated`, tout révoqué pour `anon`/`authenticated` puis `SELECT` rendu ; écritures service_role uniquement (`scan-tokens`, `label-outcomes`) ; `check` sur chaque colonne (base58, liste blanche de presets/zones, `entry_dex_id` `^[a-z0-9_-]{1,32}$`, plages) ; unique `(preset, mint)`. `performance_breakdown()` : `security invoker`, `search_path = ''`, sans argument, ne renvoie que des agrégats de tables déjà lisibles par `authenticated`, `EXECUTE` à `authenticated` seul |
| Appel direct des fonctions SQL internes | Un utilisateur appelle `rpc('x3_backfill_candidates')`, `rpc('x3_snapshot_history')` ou `rpc('apply_alert_tracking')` (pour falsifier le suivi de ses alertes ou de celles d'un autre) | `EXECUTE` révoqué de `public`, `anon`, `authenticated` (accordé à `service_role` seul), `security invoker`, `search_path = ''`, entrées bornées (≤ 200 mints, ≤ 48 h, ≤ 500 lignes ; `apply_alert_tracking` : ≤ 1000 lignes, positions ouvertes seulement, `first_hit` jamais réécrit) |
| Falsification du suivi des alertes | Un utilisateur modifie `entry_price`, `first_hit` ou `followup_sent_at` de son `alert_log` | `alert_log` : politique **SELECT seule** (propriétaire), privilège `SELECT` seul pour `authenticated`, écritures service_role (`scan-tokens`) ; `check` sur chaque colonne (prix > 0 et < 1e12, `stop < entrée < objectif`, `first_hit` ∈ {target, stop} avec `first_hit_at` associé, `tracking_until` ≤ envoi + 8 j) |
| Falsification du paper trading (v2) | Un utilisateur se crédite des SOL fictifs, crée une position déjà « exécutée » à un prix choisi, écrit une sortie ou un P&L, ajoute une jambe, agit sur la position ou le portefeuille d'un autre, lie sa position à l'alerte d'un autre ou appelle `paper_apply_v2` | RLS sur `paper_wallets`, `paper_positions`, `paper_legs` : politique **SELECT propriétaire seule** ; **aucun** privilège INSERT/UPDATE/DELETE pour `authenticated` (tout révoqué, TRUNCATE/REFERENCES/TRIGGER/MAINTAIN compris, puis `SELECT` seul rendu) ; `anon` rien. Aucune donnée de wallet réel : simulation seulement |

## Clé anon Supabase : pourquoi elle est dans le front
Elle est **publique par conception**. Elle n'ouvre que ce que la RLS autorise : ici, rien pour `anon`. Ce qui doit rester secret : la `service_role`, `CRON_SECRET` et `VAPID_PRIVATE_KEY`, qui ne vivent que dans les secrets Supabase. La clé publique VAPID (`VAPID_PUBLIC_KEY`) est publique par conception (le navigateur en a besoin pour s'abonner).

## Secrets des Edge Functions (noms uniquement)
- `scan-tokens` : `CRON_SECRET` (obligatoire) ; `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (alertes push, ignorées si absents).
- `label-outcomes` : `CRON_SECRET` (obligatoire, le même que `scan-tokens`). GeckoTerminal sans clé. Cron : `supabase/sql/schedule_label.sql` (lit l'URL et le secret dans Vault, aucun secret dans le fichier).
- `enrich-tokens` : `CRON_SECRET` (obligatoire, le même que `scan-tokens`) ; `JUP_API_BASE`, `JUP_API_KEY` (optionnels : sans eux, `lite-api.jup.ag` gratuit sans clé). GeckoTerminal et RugCheck sont appelés sans clé. Le cron (`supabase/sql/schedule_enrich.sql`) lit l'URL et le secret dans Vault : le fichier ne contient aucun secret.
- `paper-engine` : `CRON_SECRET` (obligatoire, le même que `scan-tokens`) ; `JUP_API_BASE`, `JUP_API_KEY` (optionnels). Cron : `supabase/sql/schedule_paper.sql` (Vault, aucun secret dans le fichier).
- `backtest-run` : `CRON_SECRET` (obligatoire, le même que `scan-tokens`). Aucun appel externe. Cron : `supabase/sql/schedule_backtest.sql` (worker chaque minute, run nocturne 03:40, purge des bougies > 30 j, purge lab-v2 03:30 ; Vault, aucun secret dans le fichier).
- `wallet-study-collect` (étude hors ligne, aucune alerte, aucun trading, aucun wallet) : `CRON_SECRET` (obligatoire, le même que `scan-tokens`) ; `HELIUS_API_KEY` (obligatoire). La clé Helius n'existe **que** comme secret Supabase : jamais dans le code, le front, git, Vault, la base, les logs ni les réponses. Lue par `Deno.env.get` dans la fonction, envoyée en paramètre `?api-key=` (seule méthode documentée par Helius) vers l'hôte fixe `mainnet.helius-rpc.com` : l'URL n'est donc jamais journalisée, et tout message d'erreur passe par `redactSecret()` (`_shared/wallet-collect.ts`) avant d'être stocké (`wallet_study_state.error`), loggé ou renvoyé. Garde-fou de coût : 10 crédits réservés en base avant chaque requête, arrêt dur à 600 000 crédits (contrainte `CHECK` sur `wallet_study_budget`).
